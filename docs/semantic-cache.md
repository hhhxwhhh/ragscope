# 语义缓存：让重复问题不再付费

用户不会用同一个句子问两次。「X1 电池多大」和「X1 的电池容量是多少」是同一个问题。
精确缓存（按 query 字符串做 key）对这类改写完全无效，而生成是整个链路里最贵、最慢的一步。

代码：`backend/app/rag/semantic_cache.py`、模型 `semantic_cache_entries`。

---

## 1. 为什么不用「再上一个向量库」

候选集是有界的：每个知识库最多 `SEMANTIC_CACHE_MAX_ENTRIES=200` 条，按最近命中排序取回，
在 NumPy 里算余弦。200 × 512 维的点积是微秒级，比一次 Redis 往返还便宜。

引入第二个向量库（或 pgvector 扩展）会带来三件事：多一个部署依赖、多一套失效逻辑、多一个
需要监控的故障点。在这个数据规模上，这些都换不来可观测的收益。**规模变了再换**——这是一条
写进 README「已知局限」的边界，而不是没想过。

---

## 2. 缓存放在检索之后，不是之前

这是这个模块最重要的一个决定。

```text
问题 → 改写 → 检索（向量 + BM25 + RRF + 重排 + 图扩展）→ 命中?
                                                      ├─ 是：复用「证据集 + 答案」
                                                      └─ 否：生成 → 写入缓存
```

缓存条目里存的不只是答案，还有**生成时使用的证据列表**：

```json
{
  "question": "X1 的电池容量是多少",
  "answer": "X1 的电池容量为 5000mAh [1]，支持 65W 快充 [2]。",
  "candidates": [{"chunk_id": "...", "content": "...", "filename": "..."}],
  "trace": {"query": "...", "counts": {...}},
  "usage": {"input_tokens": 1820, "output_tokens": 96}
}
```

命中时把 `candidates` 一起还原，`[1]`、`[2]` 才能继续指向正确的 chunk，引用抽屉和
`citation_stats` 与真实生成完全一致。

如果改成「检索前查缓存」，旧答案就会挂到新证据上：编号错位、来源对不上，而且这种 bug 只在
语料更新后出现，极难排查。

**代价**：命中时仍然跑了一次检索（本地 BGE 大约 10–30ms），省下的是生成（数百毫秒到数秒，
以及 token 费用）。这是刻意的取舍：正确性优先于省那 20ms。

## 3. 失效与边界

| 维度 | 规则 |
|---|---|
| 索引版本 | 条目带 `index_version`；文档变更会 bump 版本，旧条目立刻不可达，并在下次写入时删除 |
| Prompt 变体 | 条目带 `prompt_variant`；切换 Prompt 不复用另一种风格的答案 |
| 多轮对话 | **只在第一轮启用**。「那它呢？」这类问题同一个字符串在不同上下文里答案不同 |
| 拒答 | 不缓存。拒答取决于阈值与配置，缓存会把临时状态固化 |
| 容量 | 每 (kb, version, variant) 最多 200 条，超出按 `last_hit_at` 淘汰最旧 |
| 精确命中 | 先做归一化字符串比较（去空白/大小写/句末标点），命中则连 embedding 都不用算 |

阈值默认 **0.93**。BGE 的余弦分布比较集中，0.8 会把「X1 电池」和「X2 电池」判成同一个问题；
0.97 又几乎只能命中逐字改写。0.93 是在演示语料上人工核对过的折中，配置项可调。

---

## 4. 观测

- `ragscope_semantic_cache_total{result="hit|miss|store|error"}`：命中率与写入量；
- `/api/v1/ops/summary` 的 `semantic_cache` 字段直接给出这三个计数；
- 回答的 trace 里带 `semantic_cache_hit` 与 `semantic_cache_score`，聊天页会显示
  「命中了相近问题的历史回答（相似度 0.961），本次未调用模型」；
- 日志里记录命中时的原始问题，方便核对是不是误命中。

**怎么验证它有用**：连问两次同义问题，第二次的 `latency_ms` 会显著下降、`token_usage` 为空，
且 `/ops/summary` 的 `hit` +1。评测工作台走的是 `retrieve()`，不经过答案缓存，所以指标不会被
缓存污染。

---

## 5. 已知局限

- 只缓存首轮、完整答案；流式回答在命中时是「一次性回放」，不是逐字流。
- 没有做语义去重后的答案合并：两条相似条目的分数接近时，取最近命中的那条。
- embedding 存在 JSONB 里，读出来要反序列化；条目上限 200 时无感，上千条时应换 pgvector。
- 缓存不区分用户：当前权限模型下知识库属于单一用户，若将来引入 workspace 共享，需要把
  `kb_id` 换成 `(workspace_id, kb_id)` 并确认共享范围。
