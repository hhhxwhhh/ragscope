# 应用场景：消费电子售后知识助手

RAGScope 的演示租户是「星河科技」——一家做智能手表、手环和运动耳机的消费电子公司。售后团队每天要回答大量关于续航、防水、保修、配对和固件升级的问题，答案散落在产品手册、售后政策和 FAQ 里。

这个项目把这三类文档变成一线坐席可检索、可引用、可评测的知识底座：坐席用自然语言提问，系统给出带来源编号的回答；运营能看到每次检索的完整过程；质检用固定用例判断一次知识库或检索配置的改动是不是真的有效。

> 一句话：**让售后坐席在 30 秒内找到一条能直接回复用户、且经得起追问的答案。**

## 为什么选择这个场景

- **问题是真实且集中的**：售后问题重复率高、口径要求严格，答错会直接带来退换货成本和投诉。
- **答案有权威来源**：参数以产品手册为准，政策以售后条款为准，适合做引用溯源而不是让模型自由发挥。
- **天然覆盖 RAG 的难点**：既有「X1 续航多久」这种单跳事实，也有「蒸桑拿进水算不算保修」这种政策 + 产品参数的多跳问题，还有大量语料外问题需要明确拒答。
- **反馈可以闭环**：坐席的一次点踩，能直接变成下一条评测用例；知识库运营改完切块或检索配置后，可以用同一批问题验证有没有修好。

## 角色与工作流

| 角色 | 日常动作 | 项目中的能力 |
|---|---|---|
| 客服坐席 | 提问、查看引用原文、对回答点赞/点踩 | 聊天页、SSE 流式回答、`[n]` 引用抽屉、反馈 |
| 知识库运营 | 上传新版手册、处理入库失败、排查“为什么没查到” | 文档上传与重试、检索 trace、调试台 |
| 质检 / 算法 | 维护评测集、对比检索配置、看指标回归 | 评测工作台、两次 run 对比、Dashboard |
| 售后主管 | 看知识覆盖、满意度和趋势 | KPI 卡、14 天活动趋势、最近评测 |

```text
产品/政策更新
   └─ 上传文档 -> 解析 -> 切块 -> embedding -> 新 index_version
                                                    │
坐席提问 -> 多轮改写 -> 混合检索 -> 重排 -> grounded Prompt -> 流式回答 + [n] 引用
   │                                                        │
   └─ 点踩 / 拒答 ──> 一键转评测用例 <── 评测运行 <── 调整检索配置
```

## 四个演示剧本

### 剧本 1：单跳事实，验证引用能落到原文

- 模式：普通 RAG
- 提问：`X1 的续航是多久？`
- 预期：回答典型使用 14 天、重度使用 7 天，并带 `[n]` 引用；打开来源抽屉能看到《智能手表 X1 产品手册》和对应章节。
- 讲解点：回答不是凭空生成，引用编号、chunk、页码和原文在服务端一起落库。

### 剧本 2：多轮追问，验证 query 改写

- 模式：普通 RAG
- 第一问：`X2 和 X1 有什么区别？`
- 追问：`那续航呢？`
- 预期：trace 里 `rewrite_applied=true`，改写后的 query 类似「X2 和 X1 的续航有什么区别」；否则「那续航呢」单独检索没有主语。
- 讲解点：改写失败或超时会回退原问题，不影响主链路。

### 剧本 3：政策 + 参数多跳，验证 Agent 模式

- 模式：Agent 检索
- 提问：`蒸桑拿导致手表进水，还在保修范围内吗？`
- 预期：Agent 先查售后政策（5 ATM 仅适用于日常佩戴和游泳，蒸桑拿进水不保修），再查产品手册确认防水等级；时间线出现 2 次以上 `search_knowledge_base`，最终回答同时引用两份文档。
- 讲解点：规划与作答分离；工具调用有预算、超时和结构化观测，失败时 fail-open。

### 剧本 4：语料外问题，验证拒答

- 模式：普通 RAG
- 提问：`如何申请美国旅游签证？`
- 预期：返回「根据现有资料无法回答这个问题」，而不是拿「申请」「旅游」等词硬凑一个答案。
- 讲解点：向量分数门槛 0.45 控制 BM25 是否启用；拒答准确率是评测集里的独立指标。

### 备用问题

- `X1 支持连接蓝牙耳机吗？`（FAQ 精确词命中，适合演示 BM25）
- `忘记充电器了怎么办？`（X1/X2 充电底座通用，79 元）
- `手表怎么升级固件？`（升级时电量需高于 30%）

## 指标口径

| 指标 | 定义 | 项目中的状态 |
|---|---|---|
| 引用有效率 | 回答中的 `[n]` 是否落在实际来源范围内 | 已实现：`messages.citation_stats` + Dashboard |
| 用户满意度 | 点赞数 /（点赞 + 点踩） | 已实现：反馈闭环 + Dashboard |
| 拒答准确率 | 不可答案例中正确拒答的比例 | 已实现：评测集不可答案例 |
| Recall@k / MRR | 相关 chunk 是否进入前 k、首个相关结果的名次 | 已实现：评测工作台 |
| P50 / P95 检索耗时 | 检索链路的分阶段延迟 | 已实现：trace + 评测结果 |
| 平均处理时长 / 首次解决率 / 转人工率 | 坐席侧业务指标 | **未实现**，需要接入工单/CRM 系统才能统计 |

最后一行是有意写清楚的边界：这个项目证明的是「知识检索与回答链路」，不是一套完整的客服工单系统。面试时主动说明这一点，比把业务指标说成已经上线更可信。

## 评测闭环怎么用在售后

当前演示集有 29 条中文用例（24 条可答、5 条语料外不可答），标注到 chunk 级。一次典型的运营动作：

1. 坐席点踩一条回答，原因填「答非所问」。
2. 一键把它转成「用户反馈回归集」里的用例，自动带上被引用的 chunk 标注。
3. 运营调整 `chunk_size`、RRF 权重或 rerank 开关。
4. 用同一数据集跑一次评测，和基线 run 对比 Recall@5、MRR、拒答准确率和 P95。
5. 只有指标确实变好，才把配置推进到线上知识库。

现有 5 组配置的实测结论是：在 15 个 chunk 的小语料上纯向量已经很强，混合检索和重排没有正收益；重排还把 P95 从 20ms 拉到 96ms。这个结论本身不是卖点，**“先测再决定要不要为组件付延迟”** 才是。

## 边界与非目标

- 不替代工单系统、CRM 或人工客服：项目不写回工单，也不做坐席排班和质检打分。
- 不做扫描件 OCR、复杂表格还原和多模态问答。
- 不做团队、RBAC 和审计日志；当前是单用户 owner 模型，越权访问统一 404。
- 不引入 LLM-as-judge：生成侧只统计引用有效性，忠实度靠人工抽检。
- 售后建议涉及安全或法律责任时，仍需人工复核；拒答是产品能力，不是失败。

## 60 秒项目介绍

> 这是一个面向消费电子售后场景的企业知识库问答平台。上传产品手册、售后政策和 FAQ 后，坐席可以用自然语言提问，回答以流式输出，并且每个事实都带 `[n]` 引用，能点开看到原文和页码。技术上用 FastAPI + PostgreSQL + Chroma，检索是 BGE 向量加 BM25，再做 RRF 融合和可选重排；生成和 Agent 分别用 LangChain 的 LCEL 和 LangGraph 的 ReAct 图。
>
> 项目真正的重点是可观测性和评测：每次回答都记录改写后的 query、四个检索阶段的候选和耗时；任意一次检索可以保存成评测用例；同一数据集可以对比不同配置的 Recall@k、MRR、拒答率和延迟。我们用 29 条用例跑过 5 组配置，发现小语料上混合检索和重排没有正收益，于是没有把它们默认打开。整套后端有 77 个测试，CI 覆盖 ruff、pytest 和前端构建。

## 简历写法（可直接改）

- 独立开发企业知识库问答平台（FastAPI、PostgreSQL、Redis、Chroma、LangChain/LangGraph、Vue 3），支持 PDF/DOCX/Markdown 解析、结构感知切块、混合检索、SSE 流式引用问答和 Agent 多跳检索，后端 77 个自动化测试、CI 全绿。
- 设计检索可观测性与评测闭环：记录 query 改写、向量/BM25/RRF/重排四阶段候选与耗时；以 29 条 chunk 级用例对比 5 组配置，定位到小语料上混合检索无正收益、重排使 P95 从 20ms 升至 96ms，据此关闭默认重排。
- 将不可答案例的拒答准确率从 20% 提升到 100%：通过向量分数门槛 0.45 决定是否启用 BM25，24 条可答案例零误拒。
- 基于 LangGraph ReAct 实现可选 Agent 模式，在步数预算、工具超时和 fail-open 约束下完成 X1/X2 多跳对比；用 `astream_events` 将工具轨迹实时推送并落库，支持前端逐步回放。
