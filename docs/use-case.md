# 应用场景：通用文档知识库问答与检索 Agent

RAGScope 不是为某一个行业写死的问答页面，而是一套**通用的文档问答底座**：上传一组文档，就能得到可检索、可引用、可评测的知识库。问答有两条路径——简单事实问题走单轮 RAG，比较、多跳和跨文档问题交给 Agent；聊天页的「自动」模式会按问题复杂度选择。

> 一句话：**把任何一组文档变成能直接提问、回答有出处、效果可度量的知识库。**

仓库自带「星河科技」消费电子售后语料作为演示数据集，因为它同时包含参数、政策、FAQ 和语料外问题，适合展示引用、多跳和拒答。它只是**一个语料样例**，不是产品边界；换成技术文档、制度流程、课程资料或研究报告，链路完全不变。

## 适用场景

| 场景 | 语料 | 典型问题 | 用到的能力 |
|---|---|---|---|
| 产品 / 技术文档 | 产品手册、API 文档、发布说明、错误码表 | `X1 的续航是多久？`、`v2 和 v3 的接口有什么不兼容？` | 单跳 RAG、型号/版本对比 Agent、引用溯源 |
| 售后 / 客服 | 售后政策、FAQ、故障排查手册 | `蒸桑拿进水还算保修吗？`、`这个故障怎么处理？` | 政策 + 参数多跳、拒答、反馈转评测用例 |
| 制度 / 流程 | 员工手册、报销规范、入职指引、审批流程 | `差旅住宿标准是多少？`、`试用期请假需要谁审批？` | 跨文档条件检索、版本追溯、引用抽屉 |
| 学习 / 研究 | 课件、论文、调研报告、读书笔记 | `这两种方法有什么区别？`、`这份报告的核心结论是什么？` | 比较型问答、多步检索、来源定位 |
| 个人知识库 | 笔记、剪藏、阅读摘录、会议纪要 | `我之前记过哪些关于 RAG 评测的内容？` | 混合检索、trace 调试、会话管理 |

这些场景共享同一条链路，差异只在语料和问题分布：

```text
上传 -> 解析 -> 结构感知切块 -> embedding -> Chroma + BM25
                                                    │
提问 -> 自动路由 ──> 单轮混合检索 ────────────────> grounded Prompt -> 流式回答 + [n] 引用
              └──> Agent 多步检索（工具循环） ────┘
                                                    │
                          trace / 引用 / 反馈 ──> 评测集 ──> 配置对比
```

## 三种问答模式

| 模式 | 行为 | 适合 | 成本 |
|---|---|---|---|
| 自动（默认） | 规则判断问题是否包含多实体/多跳信号，有信号走 Agent，否则走单轮 RAG | 日常问答，不想手动切换 | 简单问题最低；复杂问题按需增加决策调用 |
| 快速 | 只跑一次单轮混合检索（改写、向量 + BM25、RRF、可选重排） | 参数、定义、单条政策等事实问题 | 一次检索 + 一次生成 |
| Agent | 强制进入 LangGraph ReAct 循环，模型自主决定继续检索还是作答 | 比较、多跳、跨文档、需要先查目录再读邻块 | 多次模型决策 + 多次工具调用 |

### 自动模式怎么判断

规则在 `backend/app/rag/router.py`，只看显式信号：

- 比较/选择：`区别`、`对比`、`比较`、`哪个`、`分别`、`各自`、`vs`
- 多实体：两个型号用 `和 / 与 / 、 / 跟` 连接，例如 `X1 和 X2 的充电时间`
- 多部分/条件：`并且`、`同时`、`另外`、`还要`、`导致`、`还算` 等
- 多个问号：一句话里问了不止一个问题

没有信号就留在 RAG。这个偏向是刻意的：**误判成 RAG 只多跑一次检索，误判成 Agent 会多出若干次模型决策和工具调用**。规则不调用 LLM，所以不会为了省一次调用而先付一次调用；代价是它不如语义分类器灵活，遇到用户用很隐含的方式表达多跳时可能仍走 RAG。显式选择「快速」或「Agent」可以覆盖自动判断；Agent 未启用时自动模式回退到 RAG。

路由结果不会藏起来：SSE 的 `meta` 事件同时返回 `mode`（实际路径）、`requested_mode`（用户选择）和 `routing_reason`（命中的信号），前端显示「自动 → Agent / 快速 RAG」。

## 角色与工作流

| 角色 | 日常动作 | 项目中的能力 |
|---|---|---|
| 知识使用者 | 提问、看引用原文、点赞/点踩 | 聊天页、SSE 流式回答、`[n]` 引用抽屉、自动/快速/Agent 三档 |
| 知识库运营 | 上传或更新文档、处理入库失败、排查“为什么没查到” | 上传与重试、检索 trace、调试台、索引版本 |
| 质检 / 算法 | 维护评测集、对比检索配置、看指标回归 | 评测工作台、两次 run 对比、Dashboard |
| 团队负责人 | 看知识覆盖、满意度和趋势 | KPI 卡、14 天活动趋势、最近评测 |

```text
文档更新
   └─ 上传 -> 解析 -> 切块 -> embedding -> 新 index_version
                                              │
提问 -> 自动路由 -> RAG / Agent -> grounded 回答 + [n] 引用
   │                                          │
   └─ 点踩 / 拒答 ──> 一键转评测用例 <── 评测运行 <── 调整切块或检索配置
```

## 演示语料

「星河科技」是一家虚构的消费电子公司，仓库里有 5 篇文档、15 个 chunk：

- 《智能手表 X1 产品手册》《智能手表 X2 产品手册》
- 《售后保修政策》
- 《常见问题 FAQ》
- 《固件升级说明》

评测集有 29 条中文用例（24 条可答、5 条语料外不可答），标注到 chunk 级。下面的剧本都用这套语料，换成任何一组文档后操作方式相同。

## 五个演示剧本

### 剧本 1：单跳事实 —— 自动模式留在 RAG

- 模式：自动
- 提问：`X1 的续航是多久？`
- 预期：没有多跳信号，路由到快速 RAG；回答给出典型使用 14 天、重度使用 7 天，带 `[n]` 引用；来源抽屉能看到《智能手表 X1 产品手册》和对应章节。
- 讲解点：路由不额外调用模型；引用编号、chunk、页码和原文一起落库。

### 剧本 2：多轮追问 —— query 改写

- 模式：自动（两轮都没有多跳信号）
- 第一问：`X2 和 X1 有什么区别？`
- 追问：`那续航呢？`
- 预期：第一问命中的比较信号会走 Agent；追问在 RAG 路径里触发改写，trace 显示 `rewrite_applied=true`，改写后的 query 类似「X2 和 X1 的续航有什么区别」。
- 讲解点：改写失败或超时会回退原问题，不影响主链路；路由是逐轮判断的，不继承上一轮的模式。

### 剧本 3：政策 + 参数多跳 —— 自动升级到 Agent

- 模式：自动
- 提问：`蒸桑拿导致手表进水，还在保修范围内吗？`
- 预期：命中 `导致` 多跳信号，路由到 Agent；Agent 先查售后政策（5 ATM 仅适用于日常佩戴和游泳，蒸桑拿进水不保修），再查产品手册确认防水等级；时间线出现 2 次以上 `search_knowledge_base`，最终回答同时引用两份文档。
- 讲解点：规划与作答分离；工具调用有预算、超时和结构化观测，失败时 fail-open。

### 剧本 4：语料外问题 —— 拒答

- 模式：自动（留在 RAG）
- 提问：`如何申请美国旅游签证？`
- 预期：返回「根据现有资料无法回答这个问题」，而不是拿「申请」「旅游」等词硬凑答案。
- 讲解点：向量分数门槛 0.45 控制 BM25 是否启用；拒答准确率是评测集里的独立指标。

### 剧本 5：手动覆盖自动路由

- 模式：快速 / Agent
- 操作：同一问题 `X2 和 X1 有什么区别？` 分别用「快速」和「Agent」各问一次。
- 预期：快速模式一次检索后直接回答；Agent 模式出现工具时间线和多次检索。对比两者的延迟、引用数量和回答完整度。
- 讲解点：自动只是默认策略，不是限制；所有模式共用同一套 grounded Prompt、引用编号和 trace 格式。

### 备用问题

- `X1 支持连接蓝牙耳机吗？`（FAQ 精确词命中，适合演示 BM25）
- `忘记充电器了怎么办？`（X1/X2 充电底座通用，79 元）
- `手表怎么升级固件？`（升级时电量需高于 30%）

## 指标口径

| 指标 | 定义 | 项目中的状态 |
|---|---|---|
| 引用有效率 | 回答中的 `[n]` 是否落在实际来源范围内 | 已实现：`messages.citation_stats` + Dashboard |
| 用户满意度 | 点赞数 /（点赞 + 点踩） | 已实现：反馈闭环 + Dashboard |
| 拒答准确率 | 不可答案例中正确拒答的比例 | 已实现：评测集不可答案例 |
| Recall@k / MRR | 相关 chunk 是否进入前 k、首个相关结果的名次 | 已实现：评测工作台 |
| 路由准确率 / Agent P-R-F1 | 自动模式是否把问题送到合适的链路 | 已实现：用例 `expected_mode` + 路由评测报告 |
| Agent 成功率 / 平均步数 / token | Agent 运行的健康度与单次成本 | 已实现：`agent_runs` 聚合 + Dashboard |
| 生成拒答准确率 / 误拒答率 | 换 Prompt 后，不可答问题是否仍拒答、可答问题是否被误拒 | 已实现：可选生成评测 + 确定性拒答识别 |
| 回答引用合规率 | 未拒答答案是否至少有一个有效 `[n]`，且没有越界编号 | 已实现：可选生成评测 |
| 生成耗时 / token | Prompt 改动带来的成本变化 | 已实现：生成评测按用例记录并聚合 |
| P50 / P95 检索耗时 | 检索链路的分阶段延迟 | 已实现：trace + 评测结果 |
| 平均处理时长 / 首次解决率 / 转人工率 | 业务侧工单指标 | **未实现**，需要接入工单/CRM 系统才能统计 |

最后一行是有意写清楚的边界：这个项目证明的是「知识检索与回答链路」，不是一套完整的客服工单或其他业务系统。面试时主动说明这一点，比把业务指标说成已经上线更可信。

## 评测闭环怎么用

当前演示集有 29 条中文用例，标注到 chunk 级。一次典型的运营动作：

1. 用户点踩一条回答，原因填「答非所问」。
2. 一键把它转成「用户反馈回归集」里的用例，自动带上被引用的 chunk 标注。
3. 运营调整 `chunk_size`、RRF 权重或 rerank 开关；如果问题出在回答措辞，则切换 Prompt 变体（`grounded` / `strict_citation` / `structured`）。
4. 用同一数据集跑一次评测，和基线 run 对比 Recall@5、MRR、拒答准确率和 P95；改 Prompt 时打开生成评测，额外看生成拒答、引用合规率和 token。
5. 只有指标确实变好，才把配置或 Prompt 推进到线上知识库。

现有 5 组配置的实测结论是：在 15 个 chunk 的小语料上纯向量已经很强，混合检索和重排没有正收益；重排还把 P95 从 20ms 拉到 96ms。这个结论本身不是卖点，**“先测再决定要不要为组件付延迟”** 才是。

## 边界与非目标

- 不替代业务系统：项目不写回工单、不做 CRM、排班或质检打分。
- 不做扫描件 OCR、复杂表格还原和多模态问答。
- 不做团队、RBAC 和审计日志；当前是单用户 owner 模型，越权访问统一 404。
- 不引入 LLM-as-judge：生成侧只做拒答和引用格式的确定性检查，忠实度靠人工抽检；生成评测默认关闭，避免日常评测产生 API 成本。
- 自动路由是确定性规则，不是语义分类器；用户始终可以手动指定模式。
- 涉及安全、法律或财务的建议仍需人工复核；拒答是产品能力，不是失败。

## 60 秒项目介绍

> 这是一个通用的文档知识库问答平台，上传产品手册、技术文档、制度流程或课程资料，就能用自然语言提问。回答流式输出，每个事实都带 `[n]` 引用，可以点开看到原文和页码。问答有两条路径：简单问题走单轮混合检索，比较和多跳问题交给基于 LangGraph ReAct 的 Agent；默认的自动模式用确定性规则在两者之间选择，不额外调用模型。
>
> 技术上用 FastAPI + PostgreSQL + Chroma，检索是 BGE 向量加 BM25，再做 RRF 融合和可选重排；生成和 Agent 分别用 LangChain 的 LCEL 和 LangGraph。项目真正的重点是可观测性和评测：每次回答都记录改写后的 query、四个检索阶段的候选和耗时；任意一次检索可以保存成评测用例；同一数据集可以对比不同配置的 Recall@k、MRR、拒答率和延迟。我们用 29 条用例跑过 5 组配置，发现小语料上混合检索和重排没有正收益，于是没有把它们默认打开。CI 覆盖 ruff、pytest 和前端构建。

## 简历写法（可直接改）

- 独立开发通用文档知识库问答平台（FastAPI、PostgreSQL、Redis、Chroma、LangChain/LangGraph、Vue 3），支持 PDF/DOCX/Markdown 解析、结构感知切块、混合检索、SSE 流式引用问答，以及单轮 RAG 与 Agent 多跳检索，CI 全绿。
- 设计自动路由：用确定性规则识别比较、多实体和多跳信号，在 RAG 与 LangGraph ReAct Agent 之间选择，避免为简单问题增加模型调用；路由结果、请求模式和原因随 SSE 返回，Agent 关闭时自动回退。
- 设计检索可观测性与评测闭环：记录 query 改写、向量/BM25/RRF/重排四阶段候选与耗时；以 29 条 chunk 级用例对比 5 组配置，定位到小语料上混合检索无正收益、重排使 P95 从 20ms 升至 96ms，据此关闭默认重排。
- 将不可答案例的拒答准确率从 20% 提升到 100%：通过向量分数门槛 0.45 决定是否启用 BM25，24 条可答案例零误拒。
- 基于 LangGraph ReAct 实现有界 Agent：步数预算、工具超时和 fail-open；用 `astream_events` 将工具轨迹实时推送并落库，支持前端逐步回放。
