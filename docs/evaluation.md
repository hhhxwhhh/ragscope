# 评测设计

RAGScope 的评测只回答一个问题：**换一种检索配置，相关 chunk 是不是更容易出现在最终送给 LLM 的前 k 条里？**

因此 v1 是 retrieval-only：不调用 LLM、不需要人工打分、同一份数据集重复运行结果一致。生成质量通过引用编号和人工抽检观察，不纳入自动指标。

## 数据集

演示语料是 5 篇虚构的「星河科技」产品文档，按 `chunk_size=400, chunk_overlap=60` 切成 15 个 chunk。演示数据集包含 29 条中文用例：

- 24 条可答案例：问题能在语料中找到答案，标注 1~2 个相关 chunk。
- 5 条不可答案例：问量子计算、红烧肉、美国签证等语料外内容，`relevant_refs=[]`。

用例结构：

```json
{
  "question": "X1 的续航时间有多久？",
  "relevant_refs": [
    {"document_id": "...", "chunk_index": 0, "filename": "02_智能手表X1产品手册.md"}
  ],
  "answerable": true,
  "expected_mode": "rag",
  "notes": "可选的人工备注"
}
```

约束：

- 可答案例至少标注一个 chunk；不可答案例不允许标注。Pydantic 在请求层直接拒绝（422）。
- 新增或删除文档后旧标注可能失效，因此数据集快照创建时的 `chunk_size / chunk_overlap`。改了切块参数，运行直接 409，而不是拿旧编号去打分。
- 标注只存 `(document_id, chunk_index)`，filename 由服务端根据数据库补齐，不信任客户端传入。

### 用户反馈回归集

除了手工标注的演示集，系统还有一条把线上问题沉淀为回归样本的路径：对回答点踩后点「转为评测用例」，服务端会：

1. 取该回答前一条用户消息作为 `question`；
2. 把该回答实际引用的 citation 对应的 `(document_id, chunk_index)` 作为 `relevant_refs`；
3. 如果回答是拒答、或没有任何引用，则 `answerable=false`，不传标注；
4. 写入自动创建的数据集「用户反馈回归集」，同一问题重复转换时复用已有用例。

这样反馈不再只是 Dashboard 上的一个数字：修完检索或 Prompt 之后，可以在这份数据集上跑一次，确认原先点踩的问题有没有真正被修好。注意引用的 chunk 不一定就是"包含答案"的 chunk，所以转换后的用例仍建议人工复核。

## 指标

对单条可答案例，设相关 chunk 集合为 $R$，最终检索顺序为 $r_1, r_2, \dots$：

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| Recall@k | 前 k 条中命中的相关 chunk 数 / 相关 chunk 总数 | 需要的信息找全了吗 |
| Hit@5 | 前 5 条是否至少命中一个相关 chunk | 最常用的上下文窗口够不够 |
| MRR | $1 / \text{第一个相关 chunk 的排名}$ | 第一条相关内容出现得够不够靠前 |
| 拒答准确率 | 不可答案例中返回 0 条候选的比例 | 语料外问题会不会硬答 |
| 误拒答率 | 可答案例中返回 0 条候选的比例 | 该答的有没有被拒掉 |
| P50/P95 延迟 | 检索总耗时分位数 | 质量提升值不值这些延迟 |

聚合规则：

- 出错用例计入 `cases_total` 和 `errors`，但不参与质量指标平均。
- Recall / Hit / MRR 只在可答案例上平均；拒答两个指标分别只在不可答 / 可答案例上平均。
- 延迟在全部成功用例上计算分位数，不做截断。

## 路由评测

检索评测回答「资料找没找到」，路由评测回答另一个问题：**自动模式有没有把问题送进更合适的那条链路？**

每条用例可以额外标注 `expected_mode = rag | agent`。报告在读取时现场计算，不落库、不排队、不检索、不调模型：

```text
GET /eval/datasets/{id}/routing-report
  ├─ 读取该数据集的全部用例
  ├─ choose_mode(question) -> 预测路径与命中信号
  ├─ 只有 expected_mode 非空的用例进入指标
  └─ 返回 accuracy / Agent P-R-F1 / 混淆矩阵 / 逐条对照
```

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| 准确率 | 预测路径 = 期望路径的比例 | 整体路由质量 |
| Agent precision | 真正该走 Agent 且走了的比例 / 所有被预测为 Agent 的比例 | 升级是否过度，直接对应额外延迟和成本 |
| Agent recall | 真正该走 Agent 且走了的比例 / 所有期望走 Agent 的比例 | 多跳问题有没有被漏掉 |
| Agent F1 | precision 与 recall 的调和平均 | 两个方向失衡时的单一参考 |
| 混淆矩阵 | `rag→rag / rag→agent / agent→rag / agent→agent` | 看清错误方向，而不只是一个总分 |
| 预测 Agent 比例 | 预测为 Agent 的用例 / 全部用例 | 线上成本预算的代理指标 |

未标注用例的 `correct` 为 `null`：它们仍出现在报告里，方便补标，但不进入准确率和混淆矩阵；`predicted_agent_rate` 的分母是全部用例，因为它描述的是路由器的行为，而不是标注质量。

标注是人工判断，而不是路由器输出，否则指标永远 100%，失去意义。`PATCH /eval/cases/{id}` 只修改请求里出现的字段，因此显式传 `null` 可以清除标注，省略字段则保留原值。

### 演示集上的结果

| 指标 | 数值 |
|---|---:|
| 准确率 | 96.6%（28 / 29） |
| Agent precision | 66.7% |
| Agent recall | 100% |
| Agent F1 | 80.0% |
| 预测 Agent 比例 | 10.3%（3 / 29） |

混淆矩阵：`rag→rag 26`、`rag→agent 1`、`agent→rag 0`、`agent→agent 2`。唯一误判是「手表进水导致的故障能保修吗？」：`导致` 被设计为多步故障排查信号，但这句只需要查一段售后政策，于是被升级到了 Agent。

这里刻意**不为了让指标好看而修改标注或删掉用例**。误判方向也说明当前偏差是保守的：没有 `agent→rag`，即没有多跳问题被漏掉；代价是少量简单问题多跑了 Agent。由于 Agent 的成本远高于一次检索，这个方向的错误更值得持续监控。如果调整规则，应重跑路由报告，确认没有把真正的多跳问题一起降级。

## 当前结果

2026-10，15 个 chunk，29 条用例，同一 `index_version`：

| 配置 | R@1 | R@3 | R@5 | MRR | 拒答 | P95 |
|---|---:|---:|---:|---:|---:|---:|
| 向量基线（BM25 权重 0，无重排） | **85.4%** | **100%** | **100%** | **92.4%** | 100% | 20 ms |
| 混合检索（无重排） | 79.2% | 97.9% | 100% | 88.2% | 100% | 8 ms |
| 混合 + 重排 | 79.2% | 95.8% | 97.9% | 88.3% | 100% | 96 ms |
| 向量 + 重排 | 79.2% | 95.8% | 97.9% | 88.3% | 100% | 96 ms |
| 向量优先 + 重排（2 : 0.5） | 79.2% | 95.8% | 97.9% | 88.3% | 100% | 88 ms |

怎么读这张表：

1. **纯向量在这个语料上已经足够强。** 问题基本是原文改写，稠密向量几乎没有信息损失，BM25 和重排没有提升空间。
2. **重排不是免费午餐。** P95 从 20 ms 涨到 96 ms，还把「X1 和 X2 的屏幕有什么区别？」从第 1 位压到第 5 位，R@5 掉了 2 个点。交叉编码器看 query-passage 相关性，未必优化"多文档对比"的排序。
3. **BM25 在短问句上会抢排名。** 型号、错误码这类精确词命中很有价值，但也会让包含相同关键词的另一个 chunk 顶掉语义更相关的块。
4. 这些差异小于 5 个点，样本只有 29 条，**不能当成通用结论**。这张表证明的是流程和取舍方法，不是"向量检索永远更好"。

## 拒答是怎么调出来的

第一版拒答准确率只有 20%（5 条不可答问题里只拒了 1 条）。原因：

- BM25 分数没有绝对意义，语料外问题也会因为「申请」「天」等单字命中售后/FAQ 文档。
- 只看向量分数时，相关和不相关之间没有清晰边界。

最终策略：

1. 向量 top-k 先按 `min_vector_score` 过滤。
2. **只有存在过阈值的向量候选时，才启用 BM25 候选**；没有任何稠密命中就直接拒答。
3. 用可答案例的最低最高分 0.497 和不可答案例的最高分 0.382 选阈值，取 0.45。

结果：拒答准确率 100%，24 条可答案例误拒答率 0%。这个阈值是针对当前语料和模型的，换 embedding 模型或语料后必须重新标定。

## 运行与对比

前端路径：知识库详情 -> 评测 -> 新建数据集 -> 添加用例（可从检索调试台一键保存）-> 选择预设并运行。

预设：

| 预设 | 覆盖配置 |
|---|---|
| 向量基线 | `bm25_weight=0, use_rerank=false` |
| 混合检索 | `bm25_weight=1, vector_weight=1, use_rerank=false` |
| 混合 + 重排 | 同上，`use_rerank=true` |
| 向量优先 + 重排 | `bm25_weight=0.5, vector_weight=2, use_rerank=true` |

运行详情页可以按「全部 / 未命中 / 出错」过滤，展开每条用例看实际候选的分数和排名。两次运行只有在同一数据集、同一 `index_version` 下才能对比；对比页给出指标差值和逐用例 better/worse/same。

评测运行会把 `use_cache` 强制改成 `false` 并写进运行快照。缓存命中会跳过向量化和召回，耗时不可比，也会让不同配置拿到同一份候选，因此评测必须绕开缓存。多查询扩展则保留为可配置项：开启时，运行快照会记录 `use_multi_query / multi_query_count`，不同配置之间仍然可比。

延迟差值单位是毫秒，质量差值单位是百分点（pt）。

## 可复现实验

建议每次只改一个变量，并记录三件事：配置、指标、至少一条具体用例的排名变化。

1. **RRF k**：把 `rrf_k` 从 60 改成 10，观察融合更偏向头部排名后 MRR 是否变化。
2. **BM25 权重**：`bm25_weight` 从 0 试到 2，观察型号类问题的命中是否改善、FAQ 类是否变差。
3. **切块大小**：复制知识库并用 `chunk_size=200` 重新入库，重新标注后跑同一组问题，观察 Recall@3 和 chunk 数量。
4. **拒答阈值**：把 `min_vector_score` 调到 0.30 和 0.55，分别看拒答准确率和误拒答率，理解 precision/recall 的权衡。
5. **多查询扩展**：同一组用例分别用 `use_multi_query=false` 和 `true` 跑，对比 Recall@1/3 与 P95。注意扩展会多一次 LLM 调用，耗时不只体现在检索阶段。
6. **缓存影响**：在检索调试台连续发同一个问题，观察第二次 `cache_hit=true` 且耗时只剩缓存查询。评测台里这项被强制关闭，可以借此说明"测量口径"为什么要固定。
7. **路由信号**：把 `_MULTI_PART` 里的 `导致` 临时删掉，重跑路由报告。预期准确率从 96.6% 升到 100%，但「蒸桑拿导致手表进水还能保修吗」这类真正需要多步排查的问题也会被降级。这是一次典型的 precision / recall 取舍实验：先看报告，再决定是否接受。
8. **Agent 成本**：在 Dashboard 记录改动前后的 Agent 运行数、成功率、平均步数和 token 总量。路由规则一旦放宽，先涨的通常不是准确率，而是这些成本指标。

命令行复现演示数据：

```bash
cd backend
PYTHONIOENCODING=utf-8 PYTHONPATH=. .venv/Scripts/python.exe scripts/seed_demo.py
```

脚本会创建演示账号、知识库、5 篇文档和 29 条用例；评测运行在页面里手动发起，避免种子脚本偷偷调用模型。

## 局限

- 样本小且同构，指标置信区间很宽；没有做显著性检验。
- 只评检索，不评答案正确性和忠实度。引用有效性只做确定性统计（`citation_stats`，展示在回答与 Dashboard），不进入评测指标，也不判断引用内容是否真的支持结论。
- 标注是单人或模型辅助完成的，没有多人标注一致性（Cohen's kappa）。
- 路由评测只反映规则在 29 条演示问题上的表现，且只有 2 条 Agent 正例；Agent precision 的分母很小，改一条用例就可能变动十几个百分点。它适合做回归与错误分析，不足以证明路由策略在开放域上有效。
- 路由准确率把「rag 和 agent 都能答好」的问题也算成单一正确答案，实际成本不对称；线上更应关注「被误升级的请求占比 × 单次 Agent 增量成本」。
- 拒答阈值是当前语料上的经验值，不是可迁移的超参数。
- 评测执行器与 API 同进程，服务重启会中断运行（启动时标记 failed，可重跑）。
